# qa-agent-kit

Комплект для работы QA-автоматизатора (Python) с Claude Code: скиллы плюс правила и команды-этапы.
Подключаете комплект к QA-репозиторию, заполняете одну анкету и ведёте работу
командами `/start`, `/audit`, `/reconcile`, `/plan`, `/gen`, `/feature`, `/triage`. Между этапами решает человек.

Документы: **`docs/WHY.md`** (что это и чем лучше, чем просто скиллы), **`docs/GUIDE.md`** (пошаговое
руководство: подключение, настройка, добавление контекста, свои правила и скиллы, проблемы).

Принципы:

- **Новые тесты пишутся в стиле уже существующих** (базовые классы, фикстуры, нейминг, оформление шагов).
- **Репозиторий разработки только для чтения.**
- **Ничего не выдумывается.** Каждый вывод со ссылкой на источник (`файл:строка`, спецификация, требование).
  Нет данных: агент спрашивает, а не додумывает.
- **Состояние хранится в файлах**, а не в истории чата. Новая сессия подхватывает контекст из файлов.
- Без сервера, токенов и установки CLI. Нужны только Python 3.10+, git и Claude Code.

## Быстрый старт

```powershell
# 1. Клонируйте комплект (один раз на машину) и подключите к QA-репозиторию
python C:\tools\qa-agent-kit\setup_project.py C:\work\my-qa-tests

# 2. Заполните project.yml в QA-репозитории (минимум: dev_repo ИЛИ источник в sources/requirements)

# 3. Откройте Claude Code в QA-репозитории и запустите аудит
cd C:\work\my-qa-tests
claude
```

```text
/audit
```

Сначала можно сделать пробный запуск скрипта: `python setup_project.py <путь> --dry-run` (ничего не меняет,
только показывает, что будет сделано).

## Что делает setup_project.py

| Действие | Подробности |
|---|---|
| Команды в `.claude/commands/` | 7 штук, существующие и отличающиеся не перезаписываются (нужен `--update`) |
| Скиллы в `.claude/skills/` | из локальной папки, см. раздел «Скиллы» |
| Правила в `CLAUDE.md` | внутри маркеров, ваш текст не трогается; если файл уже в git, предупредит и не изменит без `--update` |
| `project.yml`, `features/_brief-template.md` | создаёт, если нет; существующие не перезаписывает |
| Хук SessionStart (`.claude/hooks/`, `.claude/settings.local.json`) | автообновление при старте сессии, см. «Свежая версия и рабочие ветки» |
| `.git/info/exclude` | служебные пути не попадут в коммиты (локально, команда об этом не узнает) |

Не делает: не запускает Claude, не клонирует репозиторий разработки (это делает `/audit`), не трогает
`.mcp.json` и `~/.claude/`, не делает commit.

Повторный запуск безопасен. `--update` обновляет команды, скиллы и блок правил до версии комплекта.

## Скиллы

Скиллы лежат в `skills/` (25 штук, из пака «Agent Mode for Python QA»; происхождение и условия в
`skills/NOTICE.md`). `setup_project.py` копирует их в QA-репо. Лицензия пака именная и запрещает передачу
другим людям, поэтому **репозиторий комплекта должен быть приватным и доступным только владельцу лицензии**,
пока автор письменно не разрешил иное. Не добавляйте в него коллег и не открывайте его публично.

Порядок поиска скиллов скриптом: `--skills-from <папка>`, переменная `QA_KIT_SKILLS`, `<комплект>/skills/`,
`~/qa-skills`. Свои скиллы добавляются в ту же папку `skills/` (см. `docs/GUIDE.md`, раздел 7).

## Анкета project.yml

Все поля подписаны внутри файла: что ожидается, в каком формате, обязательно ли, на каком этапе нужно.

| Поле | Нужно | Когда |
|---|---|---|
| `dev_repo` (url или path) | если есть доступ к коду | `/audit` |
| `sources` (OpenAPI, коллекции, HAR, стенд) | если нет кода | `/audit` |
| `requirements` (файлы, Confluence, Jira, заметки) | желательно | `/reconcile`, `/feature` |
| `conventions` (правила команды) | желательно | `/gen` |
| `env` (адрес стенда, имена переменных) | для запуска | `/gen` |
| `stack` | нет, только чтобы переопределить | `/gen` |

Минимум: `dev_repo` ИЛИ хотя бы один источник в `sources`/`requirements`. Без этого `/audit` остановится и
спросит. **Секреты в файл не пишутся**, только имена переменных.

## Сценарии

### 1. Новый проект(с тестами)
```text
/audit       разведка QA-репо (стиль, образцы) + аудит продукта; тесты не пишет
/reconcile   сверка продукта с требованиями -> docs/gap-report.md   (нужны требования)
/plan        план по модулям -> docs/automation-plan.md (status: draft)
             Вы читаете, правите и пишете «план утверждаю» -> status: approved
/gen <модуль>  тесты по утверждённому плану, запуск и отчёт
```

### 2. Кода разработки нет
Оставьте `dev_repo` пустым и заполните `sources` (Swagger, коллекции, HAR, стенд) и/или `requirements`.
`/audit` перейдёт в режим «без кода»: выводы помечаются источником и уверенностью, а раздел
«Ограничения» перечисляет, чего без кода не видно. Нет вообще ни одного источника: агент остановится и
спросит, чем руководствоваться.

### 3. Проект уже разведан, дали задачу на новую фичу
`/audit` заново **не нужен**. Новая сессия Claude Code, затем:

1. Скопируйте `features/_brief-template.md` в `features/<имя-фичи>/brief.md`, заполните (ссылки на Confluence и
   Jira, критерии приёмки, устные договорённости).
2. `/feature <имя-фичи>`: поднимет сохранённый контекст из файлов, проверит, не устарел ли профиль
   (по коммиту), прочитает описание фичи, напишет разбор фичи (`analysis.md`), карту покрытия и список кейсов.
3. Проверьте `features/<имя>/cases.md`, ответьте на открытые вопросы, замените `status: draft` на
   `approved`.
4. `/gen features/<имя-фичи>`.

### 4. Разбор результатов
```text
/triage failures [путь]   почему упали, группировка по первопричине (баг / окружение / тест / неясно)
/triage flaky [путь]      нестабильные тесты (нужна история нескольких прогонов)
/triage impact [ветка]    какие тесты запускать под изменения
/triage bug <тест>        черновик баг-репорта (только если причина подтверждена как баг)
```

## Свежая версия и рабочие ветки (автоматически)

При подключении скрипт ставит **хук `SessionStart`**: в начале каждой сессии Claude Code он сам делает
`git fetch` в QA-репозитории и показывает, где вы стоите. Безопасное делается сам, остальное только
сообщается:

| Ситуация | Что происходит |
|---|---|
| Вы на `master`/`main`, дерево чистое, на сервере есть новое | подтягивается (`git pull --ff-only`) |
| Вы на `master`/`main`, есть незакоммиченные правки | не подтягивается, предупреждение |
| Вы на основной ветке в принципе | предупреждение: работать лучше в рабочей ветке (`/start <имя>`); агент файлы тестов в основную ветку не пишет |
| Рабочая ветка отстаёт от основной | предупреждение (merge или rebase делаете вы) |
| У комплекта есть новые коммиты, в нём нет локальных правок | комплект подтягивается и применяется к проекту (`--update`) |
| Нет сети или доступа | предупреждение, работа продолжается по последним известным данным |

**Ветку хук сам не создаёт и не переключает**, это делает только команда `/start <имя>` по вашей просьбе:
`fetch`, обновление основной ветки без слияний, создание рабочей ветки от неё. `/gen` и `/feature` на
основной ветке остановятся и предложат `/start`.

Обращение к сети не чаще раза в 10 минут. Отключить: `QA_KIT_NO_AUTOUPDATE=1` (не обновлять комплект,
только сообщать), `QA_KIT_NO_SYNC=1` (хук полностью), или подключить без хука: `setup_project.py --no-hook`.
Подробности и ручное подключение: `docs/GUIDE.md`, раздел 12.

## MCP (Confluence, Jira)

Скрипт `.mcp.json` не трогает: какой MCP-сервер использует ваша компания, зависит от Confluence/Jira
(облако или on-prem). Подключите его по документации сервера в `.mcp.json` QA-репозитория (токены только в
переменных окружения). В `project.yml` (`requirements.confluence/jira`) укажите, какие страницы и задачи
читать. Если MCP не подключён, агент скажет об этом и не будет придумывать содержимое страниц.

## Где лежат результаты (в QA-репо, в git не попадают)

| Файл | Что |
|---|---|
| `artifacts/qa-profile.json` | как устроен QA-репо: стек, структура, образцы, нейминг, как запускать, «запахи» |
| `artifacts/source-inventory.json` | карта продукта (роуты, модели, права, события), с источниками |
| `artifacts/test-matrix.json`, `artifacts/coverage-map.json` | матрица кейсов, карта покрытия |
| `docs/test-plan.md`, `docs/gap-report.md`, `docs/automation-plan.md` | планы и расхождения |
| `features/<имя>/` | бриф, покрытие, кейсы по фиче |

Если результаты нужны команде, коммитьте нужные файлы осознанно (по умолчанию они в `.git/info/exclude`).

## Правила, которые агент соблюдает (из CLAUDE.md)

Репозиторий разработки только для чтения. Тест не подгоняется под текущее поведение: при падении сначала
определяется причина (баг продукта, неясное требование, ошибка теста), решение за вами. Тесты не
запускаются против боевых окружений. Секреты не копируются. `commit`, `push`, смена веток и удаление файлов
только по вашей команде. Нет данных: вопрос, а не догадка.

## Что проверено и что нет

Проверено на практике:
- `/audit` на репозитории `search_by_tables_test`: остановка на пустой анкете с вопросами; разведка QA-репо с
  `qa-profile.json` (пять утверждений агента сверены с файлами, все подтвердились; две неточности он
  отметил сам, самопроверка добавлена после этого прогона и сама не прогонялась).
- Хук автообновления (`hooks/qa_sync.py`): 10 сценариев на локальных «серверах» (подтягивание на основной ветке,
  правки не затираются, отставание ветки, нет сети, не git-репо, троттлинг, обновление комплекта, комплект с
  локальными правками, отключение переменными); слияние с существующим `settings.local.json`; в настоящей
  сессии Claude Code агент увидел блок хука и предложил `/start`.
- `setup_project.py` на временных репозиториях: пробный запуск, установка, повтор, существующий
  `CLAUDE.md` в git, `--update`, нет скиллов, нет git, неверный путь.

Не проверено:
- Команда `/start` (создание ветки) ни разу не запускалась; хук запускался на Windows, на macOS/Linux и
  на корпоративной VDI с ограниченной сетью не проверялся.
- `/audit` с реальным кодом разработки и со спецификацией (режим «без кода» с источником), индекс кода
  (code-graph-analyzer), `/reconcile`, `/plan`, `/gen`, `/feature`, `/triage` не запускались ни разу.
- Подключение Confluence/Jira через MCP.
- Работа на корпоративной VDI с ограниченной сетью (скрипту нужен только Python, `/audit` по `url` нужен git-доступ).

Ограничения подхода: без кода разработки выводы опираются на спецификацию и стенд и надёжны настолько,
насколько они актуальны; скрытое поведение и реальные проверки на бэкенде не видны. Оценки приоритетов и
трудоёмкости приблизительные. Результат агента всегда нужно проверять, особенно ссылки на источники и
выводы «не найдено».
