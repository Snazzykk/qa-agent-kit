# Стиль Python API-тестов

## Выбери режим по рабочему репозиторию

Прочитай правила проекта, `project.yml` и существующий `artifacts/qa-profile.json`, если они есть.
Проверь живые тесты и инфраструктуру, включая незакоммиченные изменения. Приоритет: явно заданные
правила команды, ближайшие действующие тесты, затем этот образец. Авторизацию на генерацию и запуск
бери из текущей задачи и утверждённого плана; сам скилл её не предоставляет.

- **Есть действующие тесты или каркас:** расширяй их. Образец `python-api-template` не основание
  менять архитектуру, зависимости, классы на функции или функции на классы.
- **Тестов и инфраструктуры нет, нужен Python API:** используй выбранный пользователем blueprint
  [python-api-template.md](references/python-api-template.md). Он задаёт архитектуру, а поведение продукта
  определяют требования и спецификация текущего проекта.
- **Нужен UI, mobile или другой стек:** согласуй подход по задаче; этот Python API-каркас не подходит.

## Существующий проект

1. Для конкретной задачи найди ближайший тест того же ресурса и типа проверки. Прочитай его вместе
   с реально используемыми фикстурами, клиентом, моделями, assertions и подготовкой данных.
   Общий эталон всего репозитория используй, только если подходящего локального примера нет.
2. Сохраняй найденные соглашения в `style_profile` внутри **существующего** `artifacts/qa-profile.json`:
   `mode` (`existing` или `bootstrap`), `test_shape`, `layout`, `reference_tests`, `fixtures`, `clients`, `assertions`, `data_helpers`,
   `markers`, `run_command`. У примеров и зависимостей указывай относительный путь и символ/строку.
   Сохраняй остальные поля профиля; неизвестные сведения отмечай, а не заполняй догадкой.
3. Перед записью коротко назови эталон, переиспользуемые зависимости и будущий путь теста.
   Создавай новый helper, клиент или зависимость, когда существующие действительно не покрывают задачу.
4. Проверяй готовый diff по этим же примерам: форма теста, пути, сигнатуры фикстур, вызовы клиентов,
   assertions, декораторы и управление данными. Перечисли отклонения и их причину. Запусти принятые
   в проекте проверки, доступные и разрешённые для задачи; укажи, что осталось непроверенным.

Форматирование не доказывает соответствия архитектуре. Проверка результата должна обнаруживать и
параллельный HTTP-клиент, и обход принятой фикстуры, и выдуманный идентификатор кейса.
Ожидания сверяй с требованиями: баг в старом тесте не становится новым требованием.

## Пустой Python API-проект

Прочитай reference, сопоставь минимальную структуру с требованиями и выбранным стеком. Для этого
пользователя `python-api-template` уже выбран как архитектурный образец; дополнительные слои
добавляй по реальной потребности. В новых проектах предпочтительны функции pytest, `api` с клиентами
ресурсов, общий `HttpClient`/`ApiResponse`, DTO/raw-вызовы, Allure helpers и yield-фикстуры данных.

Переносимый минимальный каркас лежит в `assets/python-api/`. Он содержит **учебный ресурс demo_item
с подставным транспортом**, который не описывает продукт и не требует стенда. Создай каркас так:

```text
python <папка-этого-скилла>/scripts/bootstrap.py <QA-репозиторий> --dry-run
python <папка-этого-скилла>/scripts/bootstrap.py <QA-репозиторий>
```

При явном запросе пользователя на каркас выполняй уже разрешённую работу без повторного согласования.
Скрипт заранее проверяет конфликты и связанные пути и сохраняет существующие файлы. Устанавливать зависимости
следует в окружение проекта из его `requirements.txt`. Из корня каркаса `python -m pytest` проверяет
учебный цикл создания, получения, списка и удаления, а также отказ при некорректном raw-теле без сети.
В `api` для реального сервиса адрес
задаётся явно через `QA_BASE_URL`; без него внешний запрос не выполняется.

После smoke-проверки создавай прикладные клиенты, DTO, фикстуры и тесты по утверждённым требованиям.
Учебные маршруты, данные и коды ответов не являются шаблонными ожиданиями реального продукта.
Сохрани принятый каркас и новый живой эталон в `style_profile`; следующие задачи идут по режиму
существующего проекта.
